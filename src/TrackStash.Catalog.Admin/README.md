# TrackStash Catalog Admin

React-admin label maintenance application using React, TypeScript, and Vite. Its data provider translates the public label API into React-admin's resource contract; no database paths, SQL, or provider payload editing belong in the browser.

## Build and Use

Requirements for building: Node.js 22.12 or newer and npm. The API requires .NET 8 and an existing canonical catalog migrated to version 8 or later.

From this directory:

```bash
npm ci
npm run build
dotnet build ../TrackStash.Catalog.Api/TrackStash.Catalog.Api.csproj
```

Configure and start the API following the [module instructions](../../README.md#running-the-api-locally). Open <http://localhost:5187/admin/> and enter the same API key configured on the server.

Build the frontend **before** building/publishing the API. The API project copies the resulting assets to its output/publish directory under `wwwroot/admin`. A clean API-only build is still supported but does not include a GUI. Node/npm are not required to run an already-built/published API with these assets; creation of release installers remains future work.

Browser regressions run against an isolated API on port 5199. Playwright sends SIGTERM and allows ten seconds for fixture shutdown and removal of its disposable catalog, scanner database, artwork and backups. They do not use an existing catalog or the user API ports. If system temporary storage is unavailable, set `TMPDIR` to an approved scratch location **outside every Git working tree** before running Playwright or .NET tests; managed artwork rejects storage inside Git, including ignored directories.

The app supports:

- **Linked-audio manual choices** keep fingerprint-matching copies selectable even when ISRC or other tags disagree with an already reviewed linked copy. The Recording selector offers **Needs manual review: matches linked audio**, with visible metadata warnings; these are excluded from supported bulk selection. The linked copy's saved fingerprint/path and original accepted byte hash remain verified dependencies. No broad bypass for unrelated audio, sidecar conflicts or existing registrations.

- **Media-led Beatport admission**: **Find Release and admit** on an unlinked media row seeds Release search from its tags and retains its current-page fingerprint copies through Release/track inspection, the existing reviewed importer, and tick-and-accept linking within the same dialog. Cached non-purchase Releases are supported without purchase flags. Admission/linking are two explicit saves: linking errors retain the admitted Release and can be retried. Missing Labels still use existing Label maintenance.

- **Media matching**: filter/group the historical inventory, review up to 100 files/page, tick proposed existing Recording matches and **Accept selected** once. No reason field or second confirmation; explicit selection is recorded as judgement with permanent evidence/audits. Exact stored fingerprint copies can supply complementary tags across groups/libraries; all supporting files are frozen and verified. Conflicts/ambiguity stay explicit, and the selected batch saves atomically without assigning a whole Release group. Unmatched files remain unmatched. An independent **Unofficial / self-released** media flag is selectable/filterable, not a Label/pseudolabel or Catalog admission. Pending batch IDs survive navigation/reload in tab session storage; check the saved outcome or retry the same batch after uncertain acceptance. See [tick-and-accept workflow](../../README.md#tick-and-accept-media-worklist).

- **Expandable track rows** shared by Release, Label, Artist and Tracks pages show title/Artist, BPM, key, length and reviewed-copy count, with media locations/evidence loaded only when expanded. Recording detail keeps media collapsed under its summary header. Counts do not assert current file availability; no new media operations are included.

- **Linked Recording copies** use configurable library names and format badges, highlight exact stored audio-fingerprint groups, and fold full paths/SHA-256/link dates into **Location and file details**. Fingerprints are historical linked scanner evidence, not a fresh AcoustID or decoded-sample comparison. Missing/different fingerprints are not treated as proof of different audio.

- **Missing scanner SHA-256**: explicit individual or batch verification calculates and freezes a missing hash without scanner writes or a full rescan. Acceptance rechecks each file against its own frozen hash, including fingerprint-supporting copies. Tags can make audio-equivalent copies differ byte-for-byte. Existing scanner-hash mismatches and malformed hashes still require refreshing that file; stored audio fingerprints are not regenerated by this operation.

- **Guided media reconciliation**: group by Release and choose **Organise Release**, select an existing Catalog Release, then review proposed copies collapsed under its tracks. **Select confident matches** selects unique supported proposals together. Exceptions and tracks without copies remain separate. Verify selected files (plus supporting exact-fingerprint copies), then give one reason/confirmation to atomically save the whole-group Release association and selected Recording links with per-file and batch audits. Unselected files stay unlinked; stale or conflicting evidence blocks the batch. Continue with remaining files or check the saved outcome after uncertain/cancelled requests. No fuzzy AcoustID matching, automatic identity acceptance, new tracks, scanner changes or media moves. Individual reviews and metadata-only association remain advanced options. See [guided reconciliation](../../README.md#guided-release-and-track-reconciliation).

- **System → Libraries** (also **Media → Manage libraries**) edits library names, absolute directory roots and enabled state, and adds up to 32 libraries. IDs are stable/noneditable; disable unused libraries instead of deleting identities. No fixed role/name aliases. Saving requires explicit directory-access approval and the original settings ETag; stale drafts require explicit reload. Changes persist in server-side JSON deployment configuration (not included in database ZIP backups), apply without restart, and do not change scanner roots, move files or rescan. See [library settings](../../README.md#reviewed-filesystem-media-links).

- **Media** defaults to Release groups and offers selectable Label/Release/Artist/Track/exact-audio-fingerprint grouping, metadata filters and sorting. Library names come from **System → Libraries** settings, independently of drive names; paths remain in individual review detail. Groups are paged after whole-inventory grouping. Embedded-metadata candidates retain explicit SHA-256/scoped-sidecar verification and a reason/unchecked identity confirmation before Recording linking. Release groups also offer a separate reviewed, audited Catalog Release association, visible under Release Details, without creating Recording links or placements. Missing mix/version evidence stays manual; contradictory tags block Recording acceptance. No automatic scans, provider lookups, audio copies or ownership inference. Verification may hydrate cloud files. Recording detail lists accepted copies, not fresh presence/backup coverage. Reviewed writes require schema 13; see [media configuration and workflow](../../README.md#reviewed-filesystem-media-links).

- **Reviewed enrichment** on Recordings and Release Details offers SonoVault or Beatport, with frozen per-field proposals, original ETag, reason/confirmation, immutable audit and replay. On schema 13, **Review matched tracks for candidate** adds Beatport Release-to-Recording batches: only confident unique accepted-ID or supported ISRC/title/mix/Artist matches are writable. Missing fields default selected; overwrites and identity acceptance do not. Ambiguous/unmatched rows remain read-only. All selected Recording updates succeed atomically or roll back, affect every appearance of each Recording, and do not assert purchases/media ownership or attach artwork. The batch uses the existing schema-13 storage without another migration.

- **Artists** in the left menu: paginated name/sort-name/alias search and primary/remixer role filter, linked from Release/track credits and Label release lists. Browsing requires schema 9+; unresolved compounds remain explicit with no automatic splits/merges or identity edits.
- Artist detail tabs are **Featured, Tracks, Releases, Associations, Details**, initially Featured, with persistent portrait/name/Favourite/links/Edit header and URL tab/independent page state. On schema 12, edit bounded manual biography/source URL, typed links, Favourite, private notes/review. Drafts keep the original ETag; stale writes require explicit reload. Notes appear only in Details, not Featured. Numeric Beatport IDs generate safe Artist links, preferred first, without fetching or changing curated data.
- Use the pencil beside **Biography** to edit only biography/source while preserving other profile fields. Favourite is a heart; Beatport links use a locally bundled logo. Header links/actions have explanatory hover/focus hints. The full profile editor remains for links, notes and review.
- Click the Artist portrait/placeholder or camera (keyboard Enter/Space supported) for shared JPEG/PNG upload/replace/gallery editing with mandatory rights, immutable provenance and explicit portrait preference; there is no redundant header management link. Gallery images appear in Details; completed uploads persist while closing discards unsaved gallery edits. Protected blob images never use remote URLs or image fallbacks. Schema 9-11 keeps browsing available and shows explicit schema-12 profile/artwork guidance.
- The Artist **Tracks** tab is the shared track list filtered to this Artist: one row per credited placement, preserving repeated appearances and unplaced Recordings, newest release first by default. Search, sort and page live in the URL (`trackQ`, `trackSort`, `trackPage`). Expand **Track details** for the viewed Artist's roles/spellings with hover/keyboard-focus evidence icons. The **Releases** tab keeps compact numbered release rows with release-level contributors and BPM slots. Both lists use the release's publish date, falling back to new-release date when absent. Musical metadata remains explicitly unavailable until supported; backfill is on hold. Associations is explicitly a sketch, with no fabricated counts.
- The Label's **Artists** tab lists actual credited Artists from linked releases and their placements/Recordings, with search and primary/remixer filtering. It does not claim that those Artists are signed to the Label. Empty and unavailable states are explicit.

- **Releases** in the left menu: read-only canonical release list with title/catalog-number search and pagination. Each label's **Releases** tab shows only releases linked to that label, with its own search. Click a release title or the import outcome's **View release** link for metadata, label links, release credits and paged track placements/primary/remixer credits. Artist credits link to their detail pages. Display order is separate from source sequence and official numbering. Recording pages and release editing remain future work; this slice requires schema 9+ and does not establish purchases/media/NAS coverage.

- Release lists display a 40-pixel authenticated managed-cover thumbnail beside the title, or an album placeholder when no preferred cover is recorded. Within a Label, **Primary artist** replaces the redundant Label column and shows all release-level primary credits in order (credited spelling and unresolved markers preserved); missing credits say **Not recorded**, without borrowing track/remixer credits. The main unfiltered Releases list retains Label links. Schema 9/10 lists remain usable without artwork tables.
- Release list and track tables scroll within their own containers on narrow screens, rather than widening the page; pagination wraps to keep both controls reachable.

- Release details have a responsive managed-cover header and a Beatport logo link when a valid numeric provider ID is known, with an explanatory hint. Click the cover or empty-cover placeholder (keyboard Enter/Space also works) to open the manager; there is no redundant header management link. A camera affordance appears on hover/focus and stays visible on touch devices. On schema 11 the manager uses shared JPEG/PNG upload/replace and ordered gallery editing with explicit preference and mandatory rights. Only a preferred `cover` appears in the header; Label logos are not substituted. Closing discards unsaved gallery edits, not completed uploads. Stale writes require deliberate reload. Release browsing on schema 9/10 remains available with explicit schema-11 artwork guidance.
- Release tracks use the shared track list in release order (other sorts available), without the Release, Label and date columns already shown in the header. Rows show sequential presentation numbers across pages; presentation numbers do not change stored numbering.
- **Tracks** in the left menu, plus the Release, Label (**Tracks** tab), Artist and Recording track lists, are one component over `GET /api/v1/tracks` with different filters, so they look and behave the same. Columns: #, Title / Artist · Remixer (cover thumbnail; the title opens the Recording), Release, Label / Genre · Subgenre, Release date, BPM, Key, Length, and Releases (top level only). Each context shows a default subset, ready for future user-customisable columns. Search matches title, mix, exact ISRC, release title or credited Artist, with every word required; sort by newest/oldest release, title, Artist or release. Expand **Track details** for the release link, ISRC/IDs, display/source/official numbering, separate listing/Recording credits and provider identities.
- The top-level Tracks list shows one row per Recording (a distinct piece of audio: title, mix, ISRC), represented by its newest release with a release count. The **Recording** page shows title/mix, credited Artists, a Beatport track link when known, ISRC, length, and every release of that Recording as track listings.
- The Release artwork manager offers deliberate external candidate lookup and rights/match-confirmed attachment. No live provider adapter is registered yet: lookup reports **No external artwork providers are configured**. Candidate metadata is not a remote image preview; the browser never loads arbitrary external cover URLs. Future adapters attach validated managed copies via opaque release-scoped candidate/revision IDs and the original token. Artist provider lookup and Recording inheritance remain deferred.

- **Purchase releases**: read-only corpus queue/search and cached inspection, plus a separate immutable catalog import review on schema 10. Review each unbound Artist/Recording (pick **Same as this** on a listed match or accept a new identity; the note is optional), retain unresolved compounds where appropriate, page frozen tracks/credits and confirm apply with the checkbox (the import note is optional). Matches already bound to a different Beatport ID are not listed, so distinct same-name releases, artists and versions need no review. Decision edits supersede the old preview and reset confirmation. Blockers prevent apply; stale/expired reviews require a fresh review, never automatic retry. An accepted identical source reimport records a no-op without resetting metadata or manual order. Configure the server-defined [purchase source](../../README.md#next-reviewed-purchase-to-release-import) and restart the API. Corpus flags do not prove receipts or media ownership. Model generation, changed-graph reconciliation, provider refresh, Artist splitting and media resolution remain deferred. The GUI does not migrate databases; live schema upgrades need separate approval.
  - Click a candidate row (or its chevron) to expand inspection and import review **inside that row**; only one row is open at a time, and **Collapse** at the end of the panel returns focus to the row.
  - The **Catalog** column shows **Admitted** (linking to the catalog Release that owns the Beatport release ID), **Not admitted**, a warning when several Releases own the ID, or **Unknown** before schema 9. An import applied in the open row updates the chip immediately.
  - **Hide admitted releases** filters on the server before paging, so totals and pages stay correct. The choice is remembered in this browser. It needs schema 9+; older catalogs report an explicit error. A release you admit while it is on stays open with its outcome and leaves the list once you close it.
  - The **Ready** column shows **Ready** (complete cached source and the source label matches exactly one catalog label), **Incomplete source – N of M tracks cached** (hover for the blocker codes) or **Label needs review**. Ready is a shortlist, not approval: identity review still happens in the import review.
  - **Ready to import only** also filters on the server before paging, combines with search and **Hide admitted releases**, and is remembered in this browser. Source readiness is computed once and cached until the purchase source file changes; label matches are re-checked on every request.
  - **Batch admit ready releases** (above the search) checks every ready, unadmitted release as a dry run in groups of 25 and lists which will be admitted and which need individual review, with reasons. Tick the backup confirmation and **Admit N releases** to admit only the clear-cut ones; the list reloads afterwards. **Stop after this group** cancels between groups. New Beatport Artists/Recordings are created, compound Artists are kept unresolved, and same-ISRC-and-mix Recordings are reused; same-name Artists without a Beatport ID and unconfirmed Recording matches are left for manual review.

- **Backup type selection** separates Catalog + artwork from Scanner inventory. Scanner backup requires the server's `CatalogApi__ScannerDatabasePath` or `TRACKSTASH_SCAN_DATABASE_PATH`; without it, the option is disabled with configuration guidance. Scanner ZIPs contain the entire scanner database but no audio files or external sidecars. Retention and saved lists are separate per source/type.

- **System → Backup** in the sidebar: create a verified timestamped catalog/artwork ZIP on the server, follow progress, refresh saved archives and download the same ZIP. The newest 10 verified backups per catalog are retained. Save File-capable browsers stream downloads; other browsers have a 128 MiB in-memory limit. See [backup operations](../../docs/catalog-backups.md). No GUI restore or arbitrary browser-supplied server paths. The original `/backups` admin URL still works; an empty list is normal before the first backup. Restart the API after updating its backend, not just rebuilding the GUI.

- Inspect stable IDs, timestamps, aliases, and provider references.
- Label detail has a responsive identity header, preferred logo, biography, country name with a local flag when recognised, external-link icons, and a conditional Favourite toggle. Edit is in the header. The **Details** tab, to the right of Artists, contains the additional artwork gallery, personal notes/review status, and Record details (IDs, aliases, timestamps and link verification sources). These sections do not clutter the other tabs.
- Tabs are ordered **Releases, Artists, Tracks, Details, Relationships**, with Releases selected initially. Releases and Artists use real label-scoped search/pagination; Artists also filter by credit role. The Label Tracks tab remains explicitly not yet available. No mock records or inactive filter controls are shown.
- Stored numeric Beatport label IDs automatically provide header links opening in a new tab. Multiple IDs remain available (preferred first); a curated Beatport label URL suppresses the generated link for the same ID. Generated links use a display-name slug and the provider ID, are not written into the profile, and require no remote fetching.
- Create labels with server-assigned IDs, or edit name/sort name. Clearing sort name sends JSON null.
- In existing-label **Edit**, manage description, country/city, founded year, lifecycle, personal notes, favourite, review status, and typed links with optional verification source URL. Clear optional text/year to remove it; use the link row's remove button to remove a link. Links are displayed as safe HTTP(S) links on detail; descriptions/notes are plain text. Manual saves retain before/after history in storage, not a history-view screen.
- On **Show**, hover/focus the logo to reveal its camera action, or use **Details > Manage artwork** (touch devices also show the camera). The header uses only an explicitly preferred image; choose a preference in the manager if an existing gallery has none. Upload logos/gallery images with mandatory rights text and optional source/attribution. JPEG/PNG only, static, up to 10 MiB/25 megapixels/16384 pixels per side. Uploads save immediately; ordered gallery edits, captions, role/preference and detachment use a separate conditional save. **Replace image** keeps its gallery position and old asset/history. Reload explicitly after a stale edit. Closing the dialog discards only unsaved gallery edits, not completed uploads.
- Artwork and merge-review images use bearer-authenticated fetch and temporary blob URLs, revoked on unmount; no public asset exemption or credentials in image URLs. Originals and thumbnails are stored in the API's configured external managed directory and must be backed up with the database; see [storage configuration](../../README.md#label-artwork-and-galleries).
- Preserve the original detail-response ETag for a pessimistic conditional save. A 412 displays a stale-edit warning and does not retry or overwrite a competing edit; reload before making a fresh edit.
- The **Relationships** tab, immediately to the right of Details, contains **Label relationships**, **Groups and families**, and **Related labels**, keeping these controls off the main label page. Label relationships shows parent/imprint and distributor/distributes links with provenance, evidence and notes. **Manage relationships** edits outgoing edges; **Manage child imprints / incoming relationships** edits from the parent/distributor page. Both use paged label search, explicit review and conditional save, storing one directed edge while preserving unrelated edges. Removing a draft is not persisted until Save; Cancel makes no changes. Self-links, duplicates and imprint cycles are rejected. A changed owner/target freezes Save until deliberate Reload, which discards drafts/candidate versions and resets confirmation. No dates/territory or automatic evidence fetching yet.
- **Label groups** sits beside Labels, not under System. Create/edit distinct family/brand or organisation groups; kind is immutable. Group members and label **Groups and families** use the same reviewed membership editor and original membership/endpoint tokens. Choose current/former/unknown explicitly, record evidence and latest-period partial dates, mark departure as former, and separately confirm rejoining. Correction-only removal retains history and requires confirmation; Cancel makes no changes. No label embedding generation or automatic site fetching runs. Merge galleries retain survivor order, append retired artwork and preserve the winning preference; detached assets remain retained. ## Credentials and Browser Access

The API key is held only in JavaScript memory: not local/session storage, cookies, URL parameters, bundled environment variables, or committed files. Page reloads and explicit logout require signing in again. React-admin preferences also use a memory store, and framework telemetry is disabled.

The unauthenticated `/admin` shell and assets contain no key or catalog data. All `/api` and OpenAPI requests still require the bearer key. API and UI remain loopback-only; this is not a remote/multi-user deployment.

The built GUI uses the same origin as the API. For hot-reload development, configure the API with an explicit extra loopback origin before starting it:

```bash
export CatalogApi__AllowedOrigins__0="http://localhost:5173"
# Set CatalogApi__DatabasePath and CatalogApi__ApiKey separately, then start the API.
```

In another terminal, from this directory:

```bash
npm run dev
```

Open <http://localhost:5173/admin/>. Vite binds localhost only, uses strict port 5173, and proxies `/api` to localhost:5187. If the API uses another port, set `CatalogApi__Port` to the same value in the Vite shell. The API checks the browser's original Origin, even through this development proxy; it does not trust forwarded headers or disable authentication. Direct configured-origin access allows only GET/POST/PATCH and Authorization/Content-Type/If-Match, exposing ETag/Location without cookie credentials.

Do not put the key into `VITE_*` variables: Vite embeds those variables in public JavaScript.

## Verification

```bash
npm run lint
npm test
npm run build
npx playwright install chromium   # first browser test run only
npm run test:e2e
ADMIN_TEST_DEV=1 npm run test:e2e  # same tests through the Vite development proxy
```

Unit tests cover transport mapping, original-token preservation, rejected writes, merge review/apply, errors, and authentication. Browser tests start a temporary catalog/API and check real sign-in, detail/child display, create/edit, stale writes, searching/paging/sorting, logout/refresh, merge cancellation/confirmation/provider preservation, and stale merge rejection. They require the repository's bootstrap module and `sqlite3`, use ports 5199 (API) and optionally 5173 (Vite), and stop their servers/remove their temporary catalog on exit. Never use a live catalog for these tests.

## Dependency and Generated-file Policy

Country/territory names and flags come from the locally installed MIT-licensed `flag-icons` package; only recognised ISO entries are displayed. Unknown stored country codes remain text without inferred flags. Selected music-service SVG paths come from CC0 Simple Icons. Resident Advisor and social links currently use generic icons pending brand-asset review, while still retaining service-specific accessible names. MUI provides interface/fallback icons. All images/icons are local, apart from authenticated catalog artwork fetches; visiting a label never fetches remote site logos. Sources and flag licence text are distributed in `/admin/THIRD-PARTY-NOTICES.txt` (see [source notices](public/THIRD-PARTY-NOTICES.txt)).

Commit source, configuration, `package.json`, and `package-lock.json`; restore with `npm ci`. Do not commit `node_modules`, `dist`, local environment files, or test output. The framework is restored from npm, not copied into source control.

React-admin currently brings query-string 7, whose decoder dependency has a security advisory. The manifest overrides it to patched decode-uri-component 0.5.1 or later. Because the patch is ESM while query-string expects a CommonJS function, [the small compatibility adapter](tools/uri-decoder.cjs) exports its default function via a Vite alias. Both production and development browser suites exercise query parsing/pagination. Remove the override/adapter together when the upstream dependency is upgraded compatibly. No third-party decoder source is vendored.

The initial React-admin production bundle is roughly 1 MB before gzip (about 315 KB compressed), so Vite reports its standard large-chunk advisory. This is not a failed build; bundle splitting can be addressed as screens expand.
